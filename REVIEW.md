# Ревью: инструмент `reserve_material`

```python
@assistant_tool("reserve_material")
async def reserve_material(args: dict, db) -> str:
    """Зарезервировать материал под задание."""
    logger.info("tool call: %s", args)
    batches = await db.fetch_all(
        f"SELECT * FROM batches WHERE material_code = '{args['material']}' "
        "ORDER BY id DESC"
    )
    need = float(args["qty"])
    for b in batches:
        take = min(b["qty"] - b["reserved"], need)
        await db.execute(
            "UPDATE batches SET reserved = reserved + :t WHERE id = :id",
            {"t": take, "id": b["id"]},
        )
        need -= take
        if need == 0:
            break
    return f"Готово, зарезервировано {args['qty']}"
```

**Итог:** в таком виде мержить нельзя. Здесь SQL-инъекция, которую может запустить промпт-инъекция; нет прав и подтверждения; гонка даёт двойной резерв; порядок не FIFO; ответ модели неправдив. Ниже проблемы по убыванию важности, у каждой — как исправить. В конце — исправленная версия.

---

## Критично (блокирует мерж)

### 1. SQL-инъекция через аргумент от модели
`f"... material_code = '{args['material']}'"` подставляет строку в SQL как есть. Аргументы пишет модель, а модель пересказывает то, что прочитала: вопрос пользователя, комментарий к партии, загруженный CSV. Значит, достаточно положить в комментарий партии текст вроде `воск'; UPDATE batches SET reserved = 0; --`, попросить ассистента «разобраться с этой партией» — и запрос выполнит чужой SQL. Это не теоретическая уязвимость: промпт-инъекция превращается в SQL-инъекцию.

**Исправление:** только параметризованные запросы (или ORM); материал искать по id или по коду, который прошёл валидацию (`^[A-Z0-9_-]{1,30}$`).

### 2. Нет пользователя и проверки прав
Инструмент не знает, кто его вызвал. Кладовщик не может резервировать материалы кнопкой, но через ассистента — может. ТЗ прямо запрещает: «через ассистента нельзя сделать то, что нельзя сделать кнопкой».

**Исправление:** инструмент получает контекст с текущим пользователем из сессии (не из аргументов модели) и вызывает сервисную функцию, внутри которой стоит `require(user, Perm.JOB_MANAGE)`, — ту же, что вызывает кнопка.

### 3. Изменение данных без подтверждения
Резерв пишется в базу сразу, в момент вызова инструмента. По ТЗ данные меняются только после нажатия «Подтвердить», а до этого ассистент показывает, что собирается сделать. Сейчас любая инъекция («зарезервируй весь воск под задание X») сразу меняет склад.

**Исправление:** инструмент делает пробный расчёт без записи и создаёт «предложенное действие». Запись выполняет эндпоинт подтверждения, повторно проверив права и аргументы.

### 4. Гонка: два одновременных вызова резервируют один и тот же остаток
`SELECT` без блокировки, затем `UPDATE` по одной строке. Два параллельных запроса читают один и тот же `qty - reserved`, и оба резервируют его целиком. Кроме того, нет общей транзакции: если на третьей партии случится ошибка, первые две останутся зарезервированными, а вызывающий код об этом не узнает.

**Исправление:** всё в одной транзакции; строки партий читаются `SELECT … FOR UPDATE` в фиксированном порядке (тогда второй запрос ждёт и видит уже уменьшенный остаток, а дедлоков нет). В базе — CHECK `0 ≤ reserved ≤ on_hand` как последний рубеж. На дедлок или ошибку сериализации — одна повторная попытка.

### 5. Ответ врёт модели, а модель — пользователю
`return f"Готово, зарезервировано {args['qty']}"` возвращает запрошенное количество, а не фактическое. Не хватило остатка — цикл тихо закончился, а модель получила «Готово» и скажет пользователю, что всё зарезервировано. Нарушает требование «числа в ответе — только из результатов инструментов»: здесь результат инструмента сам по себе ложный. Дефицит теряется.

**Исправление:** возвращать структуру с фактом: сколько запрошено, сколько зарезервировано, из каких партий, какой дефицит. Частичный резерв — нормальный исход, но о нём нужно сказать.

## Серьёзно (неверная бизнес-логика)

### 6. LIFO вместо FIFO
`ORDER BY id DESC` берёт самые новые партии первыми. По ТЗ резерв по FIFO — сначала старые партии.
**Исправление:** `ORDER BY received_at, id`.

### 7. Резервируются непринятые и бракованные партии
Нет фильтра по статусу: в резерв попадут партии «На проверке» и «Брак». Использовать можно только принятые.
**Исправление:** `WHERE status = 'accepted'`.

### 8. Отрицательный `take` снимает чужой резерв
Если у партии `reserved > qty` (данные уже испорчены той же гонкой из п. 4, или `qty` — это начальное количество, а часть уже израсходована), то `take < 0`: `reserved` уменьшается (снимается чужой резерв), а `need` растёт. При `take == 0` выполняется пустой `UPDATE`.
**Исправление:** брать только партии со свободным остатком > 0 (условие в SQL), `take` всегда положительный.

### 9. Непонятно, от какого количества считать
`b["qty"] - b["reserved"]` — если `qty` это количество при поступлении, то после выдачи в цех свободный остаток будет завышен. Нужен текущий остаток (`qty_on_hand`), а не исходный.

### 10. Резерв не привязан к заданию, повтор удваивает резерв
Docstring говорит «под задание», но задания в коде нет — растёт только счётчик в партии. Такой резерв нельзя снять при отмене, нельзя списать при запуске, нельзя понять, чей он. А если модель повторит вызов (обрыв стрима, ретрай, модель «на всякий случай» вызвала дважды), резерв удвоится.
**Исправление:** таблица `reservations(job_id, batch_id, material_id, qty)`. Операция идемпотентна: «довести резерв задания до нормы», а не «добавить ещё N».

## Важно (надёжность и качество)

### 11. `float` для количеств
- `0.1 + 0.2 != 0.3`: после вычитаний `need` почти никогда не станет ровно `0`, `break` не срабатывает, и цикл проходит по всем партиям, записывая «резервы» вида `1e-16`.
- `float("nan")` и `float("inf")` проходят: с `inf` инструмент заберёт весь остаток, с `nan` все сравнения ломаются.
- Отрицательное количество принимается и снимает резервы.

**Исправление:** `Decimal` в коде и `numeric` в базе; валидация `qty > 0`, не больше 3 знаков после запятой, разумный максимум; сравнение остатка — точное на `Decimal`.

### 12. Нет валидации аргументов
Нет ключа `material` или `qty` — `KeyError`, инструмент падает. Лишние поля молча игнорируются. Модель может передать название вместо кода — запрос ничего не найдёт и вернёт «Готово». Аргументы от модели — внешний ввод, их нужно проверять как запрос из интернета.
**Исправление:** Pydantic-модель аргументов (`extra="forbid"`, типы, лимиты); ошибка валидации возвращается модели понятным текстом, чтобы она исправила вызов, а не роняет чат.

### 13. Бизнес-логика в инструменте, а не в сервисном слое
Кнопка в интерфейсе резервирует одним кодом, ассистент — другим. Любое исправление правил придётся делать дважды, и рано или поздно они разойдутся. ТЗ требует, чтобы кнопка и инструмент вызывали один и тот же код.
**Исправление:** инструмент — тонкий адаптер: валидация аргументов → сервисная функция → сериализация результата.

### 14. Нет записи в журнал изменений
Непонятно, кто и когда зарезервировал материал. По ТЗ все изменения пишутся в журнал: кто (ФИО), когда, что было, что стало.

### 15. В лог пишутся сырые аргументы
`logger.info("tool call: %s", args)` сохраняет всё, что передала модель: возможны ФИО и названия поставщиков (персональные данные в логах запрещены ТЗ) и тексты инъекций. Плюс лог можно засорить огромным аргументом.
**Исправление:** логировать имя инструмента, id вызова, id пользователя и результат проверки; аргументы — только после маскирования и с ограничением длины.

---

## Мелочи

16. `SELECT *` — тянет все колонки (включая комментарии, где может быть что угодно) и ломается при изменении схемы. Выбирать нужные поля.
17. Возвращается строка, которую модели приходится разбирать. Лучше структура (JSON) с явными полями.
18. Нет типов у `args` и `db`, docstring не описывает аргументы — модель узнаёт о них только из описания инструмента, которое тоже не видно.
19. Нет тестов. Минимум: FIFO, частичный резерв с дефицитом, два параллельных резерва, отказ без прав, отказ без подтверждения, повторный вызов без удвоения.

Инструмент — только предложение действия, без записи:

class ReserveForJobArgs(BaseModel):

    job_number: str = Field(min_length=1, max_length=20)


@assistant_tool(
    "reserve_for_job",

Запись — в сервисе, его же вызывает кнопка «Зарезервировать» и эндпоинт подтверждения:

```python
async def reserve_fifo(
    session: AsyncSession, user: User, job: Job, material_id: int, need: Decimal
) -> ReserveOutcome:
    require(user, Perm.JOB_MANAGE)
    # Блокируем свободные принятые партии в порядке FIFO: параллельный запрос подождёт
    # и после нашего коммита увидит уже уменьшенный остаток.
    batches = await session.scalars(
        select(Batch)
        .where(
            Batch.material_id == material_id,
            Batch.status == BatchStatus.ACCEPTED,
            Batch.qty_on_hand > Batch.qty_reserved,
        )
        .order_by(Batch.received_at, Batch.id)
        .with_for_update()
    )
    reserved = Decimal(0)
    parts: list[ReservedPart] = []
    for batch in batches:
        if reserved == need:
            break
        take = min(batch.qty_on_hand - batch.qty_reserved, need - reserved)  # всегда > 0
        batch.qty_reserved += take
        session.add(Reservation(job_id=job.id, batch_id=batch.id, material_id=material_id, qty=take))
        parts.append(ReservedPart(batch_number=batch.number, qty=take))
        reserved += take
    audit.record(session, user, entity="job", entity_id=job.id, action="reserved",
                 after={"material_id": material_id, "need": str(need), "reserved": str(reserved)})
    return ReserveOutcome(requested=need, reserved=reserved, deficit=need - reserved, parts=parts)
```

Вызывающий код (подтверждение действия) открывает транзакцию, блокирует строку задания (`SELECT … FOR UPDATE`, проверка статуса — защита от двойного подтверждения), для каждой строки рецепта резервирует только недостающее до нормы и коммитит всё разом.
